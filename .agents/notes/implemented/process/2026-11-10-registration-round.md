# Agent Note: 2026-11-10 登记轮

Status: implemented

## Problem

2026-11-10 登记轮开始时 `main` 为 109 条（末尾 `dsh-logo-golden`），开放 PR 46 个。其中 15 个的作者在我上次评审之后有新提交，需要逐条核对反馈是否落实；另有 33 个 PR 处于 `CONFLICTING`，原因是 `community.json` 的单文件尾部追加结构使每合入一条就让其余对准旧尾部的分支整体失配。本轮需要解决两个问题：这 15 条的内容判定，以及尾部失配造成的合入阻塞——按旧约定逐条要求作者重基，每条要一次往返，且每次合入又会重新制造失配。

## Decision

**11 个 PR 合入，`main` 由 109 条增至 119 条。** 每条都先逐句核对商店文案与上游当前发布版本，再核 diff 形态、字段合法性、兼容范围、上游可用性，并按三性（实用性 / 稳定性 / 兼容性）留证据；11 条的内容结论都是「反馈已落实、无阻塞项」。

- `#84` `dsh-cost-voice`（`cea6f03`）：商店文案补上了随包第三方素材的许可限定（Reathin/XVoice 未附许可、大白饭为 MiMo 克隆二创、图标为网友二创），展示名同步到 1.2.0。
- `#58` 三条 DDDMUC 条目文案刷新（`26dcec1`）：url-router 补 macOS 桌面地址栏、恢复「绝不覆盖外来 fragment」与「唯一写者」并存，aistudio 改 6 个 insert 行，delete-session 改 409 措辞。此条是原地修改、与尾部位置无关，因此在其他条目合入后仍可直接合并。
- `#93` `dsh-plugin-restart-button`（`af23ba5`）：我上轮点名的六条路由守卫已补（`guardRequest` 覆盖回环对端、回环 Host、Sec-Fetch-Site、同源 Origin），close request 判据同时匹配新老启动器日志；稳定性维度按「证据不足」记录（仓库无测试目录、无 CI，正文引用的用例未入库），维护者裁定按收录处理并记录该缺口。
- `#60` `dsh-novel-fish`（`cb010ed`）：删掉写死的「npm 最新 1.0.1」。
- `#86` `dsh-memory-engine`（`82779b4`）、`#81` `slumberpavilion`（`cf8bf5e`）、`#67` `dsh-assistant-photographer`（`a3ff66b`）、`#59` `dsh-llm-keypool`（`1f6fba9`）、`#55` `diy-journal`（`4ac7c18`）、`#48` `dsh-oh-my-claude`（`9d5c175`）：上轮反馈全部落实，仅剩尾部位置问题。
- `#74` `dsh-agent-web-search`（`6e2986e`）：作者在我批准后自行重基，未动用代重建。

**尾部重建改由维护者代做。** 维护者裁定：内容已核实、冲突纯粹是数组尾部位置问题的 PR，由维护者按当前 `main` 重建该条并推回作者分支，不再要求作者重基。实现方式是为每个 PR 创建一个以「作者分支头」与「当前 `main`」为双亲的合并提交，其树等于当前 `main` 的树、仅把该条追加到数组末尾，因此推送到作者分支是快进（不 force push、不丢作者提交），作者的署名与 PR 流程都保留。10 个 PR 用这条路径落地；`#74` 的作者自行重基，未走该路径。判据是分支头是否已包含当前 `main`（`git merge-base --is-ancestor`），已包含则跳过重建直接合并。

**4 条维持退回，等作者改文案。** `#89` 引擎数量随上游 11-08 加引擎漂移（条目写 35/27，0.9.41 实为 36/28）；`#83` 商店文案需补默认值与副作用（自动交接默认关、编号会改写既有会话标题且卸载不还原）；`#73`「桌宠在会话页里按需打开」第三次未改，上游 Web 端只注册侧栏与主面板两个席位、像素鲸在插件自己的 `/pet-voice/` 页与 Android 悬浮窗渲染；`#71` 上游 main 已把聚焦模式改为默认关闭，条目写死的「默认 Cmd/Ctrl+U」会随下个版本失真。

## Alternatives considered

- **继续逐条要求作者重基。** 否决：本轮 33 个 PR 处于 `CONFLICTING`，其中 11 条的内容已核实无阻塞；按旧约定每条要一次往返，且每合入一条都会再次让其余分支失配，收敛速度受制于往返次数而不是内容质量。代重建的产物经本仓校验器与真实 CI 门禁验证（每条都跑绿后才合入），并保留作者提交与署名，代价低于让贡献者反复重基。
- **让维护者把已核实的条目直接提交到 `main`，再把 PR 作为「已落地」关闭。** 否决：这会让 PR 失去合并记录与作者署名，也与「登记经 PR 评审」的既有流程冲突；代重建保留了 PR 合并这一事实。
- **对 `#93` 以「稳定性证据不足」为由继续阻塞，或要求作者补测试与 CI。** 否决：索引里多数上游条目同样没有 CI，单独对这条设更高门槛会与既有准入口径不一致；该插件的路由守卫与 45 秒看门狗已验证、失败面有界，因此按收录处理并把缺口记入评审。
